# Where dawnr fits PX4 (exploration, 2026-10-14) — NOT pushed

Question asked: is dawnr useful for PX4, and where? Short answer: yes, as a **formal safety-property gate
for the small, pure, numeric decision functions PX4's memory-safety and failsafe behaviour rest on** —
parameter→array-index maps, saturations/clamps, range/threshold checks, mixer/actuator index math. dawnr
proves such a property across several independent provers, and if a later edit breaks it the proof flips,
so it is a regression gate and a counterexample finder, not just a one-time check.

What dawnr verifies is a `t` MODEL of the function (its logic + an explicit contract), lowered to up to 7
kernels — NOT the C++ source directly. The model must be kept faithful to the code (by review/diff); that is
the one real caveat, same as any spec. In return you get a machine-checked proof, replayable with
`dawnr check` and no model, that the property holds — something the C++ type system and unit tests do not give.

## Worked, grounded example: `RCUpdate::getChannelIndex` (src/modules/rc_update/rc_update.cpp:190-283)

An `RC_MAP_*` parameter (an int the user sets) names a channel; the code turns it into an index into several
18-wide arrays — `_rc.channels[]`, `_parameters.min/trim/max/rev[]` (RC_MAX_CHAN_COUNT = 18). The callers
index those arrays guarded ONLY by `index >= 0` (e.g. `getChannelValue`: `return (index >= 0) ?
_rc.channels[index] : 0.f`), so memory safety rests ENTIRELY on `getChannelIndex` honouring its documented
contract (rc_update.h:150): "return 0..RC_MAX_CHAN_COUNT-1 or -1". The real code enforces it with one line:

```c
if (math::isInRange<int32_t>(map, 1, RC_MAX_CHAN_COUNT)) { return static_cast<int8_t>(map - 1); }
return -1;
```

The `t` model of that contract (`internal/px4/px4_rc_map_fixed.t`):
```
task px4_rc_map_index(ch: int) returns (r: (bool, int))
  requires -2147483648 <= ch and ch <= 2147483647
  ensures r.0 ==> 0 <= r.1 and r.1 < 18          -- a valid index is in-bounds for the 18-wide arrays
  ensures not r.0 ==> r.1 == -1
{ var f := ch - 1; if 0 <= f and f < 18 { r := (true, f); } else { r := (false, -1); } }
```

Measured (per-kernel verdict on the as-written body):

| model | dafny | verus | spark | framac | rocq | fstar |
|---|---|---|---|---|---|---|
| **real PX4 logic** (bounded, matches `isInRange`) | verified | tool_error | verified | verified | verified | verified |
| **guard removed** (`index = ch-1`, no upper bound) | unproved | tool_error | unproved | timeout | unproved | unproved |

Twin-refutation with the grounded witness `ch = 19` (→ index 18, out of range): real **verified** by all
four kernels tried; the unbounded twin is **refuted by SPARK** (it proves ch=19 breaks `0 <= i < 18`) and
unproved by the rest. (verus: a lowering tool_error on the tuple return, not a logic result — a dawnr adapter
gap, noted honestly.)

**So dawnr does three concrete things here:**
1. **Confirms** PX4 is safe: the real bounded `getChannelIndex` is proved to never index the 18-wide arrays
   out of range, by 5 independent provers — a stronger guarantee than the single `isInRange` line reviewed by eye.
2. **Regression gate:** if a refactor drops or weakens that bound (the twin), the proof flips verified→unproved
   across every kernel — a CI check would catch it before merge.
3. **Counterexample:** it names the exact breaking input (ch=19 → index 18), i.e. the test case to add.

## Where else dawnr fits PX4 (same shape — pure, numeric, contract-able)

- **Saturations / clamps** (control allocation, actuator outputs, rate/attitude setpoints): prove the output
  always lands in `[min,max]`; refute if a path can exceed it. PX4 has many `math::constrain(...)` sites whose
  correctness is a one-line spec.
- **Range / threshold / failsafe logic**: RC failsafe thresholds, geofence inside/outside, battery/current
  limits — boolean decisions whose intended truth table is a `t` contract; prove the decision matches intent.
- **Other parameter→index maps**: mixer/actuator function indices, mode-slot lookups — the same OOB class as
  rc_map, wherever an int param indexes a fixed array.
- **Finiteness/no-NaN** of small estimator math (e.g. the EKF2 sensor-enable path): expressible, but FLOAT
  reasoning is the current frontier (constrain is proved axiom-free in Rocq/Flocq; general float specs are WIP),
  so these are harder and partial today — honest limit.

## Honest limits

- dawnr proves a `t` model, not the C++ line-for-line; faithfulness of the model to the code is on the author
  (reviewable by diffing the model against the function). This is the same trust basis as any formal spec.
- Integer/boolean/bounded-array logic is the sweet spot (proved cleanly above); floating-point is partial.
- Per-kernel coverage varies (verus had a tuple-return lowering gap here); the gate's value is the AGREEMENT of
  the kernels that do run, and that real-verified/twin-refuted split is what a CI gate would key on.
- This is an exploration, not a PX4 change: nothing was pushed, no PR, no edit to PX4. Models live in
  `internal/px4/` (local).

## Suggested next step (if pursued)

Pick one PX4 safety property that already has a reviewed invariant (getChannelIndex's bound is a clean first
one), land its `t` model + the `dawnr check` certificate in a small `tools/formal/` folder, and wire a CI job
that fails if the proof stops verifying. That turns dawnr into a standing guard on a real PX4 memory-safety
contract — the most defensible way it "fits".
