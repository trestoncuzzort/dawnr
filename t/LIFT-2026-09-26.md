## The lifter's name for it: `source-axiom`, `source-assume` (2026-09-27)

DT0258 did not mis-translate a bitwise program: `BitwiseOr(x: int, y: int): int { 0 }` is a
placeholder, and the source's own claims about it -- `lemma {:axiom} BitwiseOrIdentity(x)
ensures BitwiseOr(x, 0) == x`, `BitwiseOrCommutative`, `BitwiseOrIdempotent` -- are Dafny
Reference Manual `{:axiom}` lemmas (11.2.4: "the post-condition may be assumed to be true
without proof"), false for that body whenever `x != 0`. Dafny verifies the source anyway,
because `{:axiom}` never checks a lemma's ensures against anything; the lift then inlines
`BitwiseOr`'s real body (t has no axioms) and every kernel correctly refutes the resulting task.
Nothing was mis-lifted; the source was never a verified program in the sense the census reports.

`lift_classify.py` now reads this at classify time, before a lift is attempted: every
`{:axiom}`/`{:verify false}` declaration and every `assume` statement in the file (LIFTER-
DECISIONS row 51), refusing `source-axiom` when the method's spec, body, invariants or closure
references an axiomatised declaration or a function whose only stated properties are axiom
lemmas, and `source-assume` when an assume lies in the method's own body or a callee's. An axiom
outside the method's reach still lifts, noted `axiom-in-file`.

**Measured** (`t/lifter.py --list`, `--skip-check --jobs 4`, desktop CPU, out under
`~/scratch/axiom/`): of the 1,886 staged files, 69 carry `{:axiom}` and 68 carry a raw `assume`
token (80 in their union; 11 of the 68 turned out to be the English word inside a comment, not
an executable statement -- the classifier's own AST-based reading never mistakes those, only the
candidate-file grep does). Over the 80: **74 methods refused** -- 61 `source-assume` directly, 10
`callee-refused:source-assume` (an assume hidden in a lemma the method calls -- invisible to
every earlier check, since `LemmaDecl.parts` is not a dataclass field and `walk()` never reached
a called lemma's own proof), 3 `source-axiom` (`DT0258`, `DT0333`, `DT0360`; DT0258 itself reads
`source-axiom` on token `BitwiseOr`, the placeholder function at its declaration). 49 methods still lift; none of the 80 files
happened to combine a lifting method with an axiom declaration it does not touch, so
`axiom-in-file` fired 0 times in this sample (`t/test_lift_source_axiom.py` exercises the note
directly, since the sample here does not).

Of the 74 newly refused methods, exactly **1** (DT0258's `NumpyBitwiseOr`) had ever lifted before
across any `t/out/lifted-tasks-*` run -- the other 73 either never had a gradable method to begin
with under an earlier lift, or were already refused there for an unrelated reason (many of the
`{:axiom}` files also carry the `assume` their own graded method already fails on). DT0258 is in
neither `~/scratch/corpus-2026-09-27-6.txt` (552 documents, graded trust) nor `-7.txt` (454
documents clean in seven): the twin/kernel gate had already excluded it by refutation, at the
cost of seven proof attempts against a spec that could never hold. **The corpus effect of this
rule today is 0 of 552 and 0 of 454 documents** -- it removes nothing already admitted, because
nothing this unsound was ever admitted; its yield is compute and honesty going forward, catching
the same defect at classify instead of after seven kernels run on it.

One thing this rule does not reach, found while measuring and left as is by the letter of the
decision: `assume{:axiom} false;` inside an unrelated, no-ensures sibling method (`vericoding_
DD0311`, `DD0520`, `DD0521`, `DD0598`, all a boilerplate `method Testing'() { assume{:axiom}
false; }` stub) sits in neither the graded method's body nor a callee it calls, so it is not
refused and gets no note; the decision names an axiom DECLARATION outside the closure for
`axiom-in-file`, not an assume statement in a method the graded one never touches.
