# Dawnr v6: improve on the shipped v5 with the corrected training data

Registered 2026-10-18 during the existing v6 training run, before any v6
development or held-out evaluation in this continuation. Training began before
this registration. The goal is an incremental measured improvement, with the
same attempt budget and checks for both models.

## Candidate and data

The in-flight candidate uses Qwen3.5-4B, NF4 with double quantization and bf16
compute, rank 64, alpha 16, dropout 0.1, all linear layers, learning rate 2e-4,
five epochs, batch 1 with 16 accumulation steps, maximum row length 2,845,
and seed 1. The trainer is `student_sft.py` at commit `a961cfba`. The input is
4,189 rows, SHA-256
`e14f766f06299d589d9a6e3293f6bf3e3f06ffac026433e2fdeff1c04294af80`.

This is not v5's original 5,095-row input with rows appended. It combines the
corrected 3,352-row reconstruction with later data and deduplicates the result.
There are 909 rows explicitly marked `judge-python` and `proof: none`; their
test results are not formal proofs. The remaining rows include specification
and repair examples and do not all represent independent proved programs.
The exact construction, provenance, deduplication, and panel checks must be
reproduced before release. A zero overlap count from the t-program audit alone
does not establish that Python rows or unparsed examples are independent.

## Comparison and release conditions

The recorded v5 reference is 17/182 at one or more kernels, 12/182 at all seven,
and 27/33 supplied specifications at all seven. These are historical results
to reproduce from saved evidence or remeasure under a common instrument, not
numbers to assume. The held-out route has 17 attempts per problem; the precise
prompts, routes, decoding settings, and model formats must be recovered and
frozen before either model's new held-out generation. Development evaluation
comes first. No held-out failure may guide the candidate's training or selection.

Predictions and acceptance conditions:

- V1: v6 solves at least one more clean-182 problem than v5 under the same
  evaluation, and at least 18 in total. Its all-seven count is at least v5's
  matched count and at least 12.
- V2: v6 proves at least as many of the 33 supplied specifications as v5 under
  the matched evaluation, and at least 27, with all seven kernels.
- V3: the installed-format candidate retains the qualifying results; an
  adapter-only result is insufficient to promote a quantized release.

Both arms use identical problem panels, prompt construction, decoding settings,
attempt budgets, and verifier/specification gates. Report missing outputs,
timeouts, parser failures, refutations, and contamination separately. Record
per-problem outcomes and uncertainty; a one-problem gain on one training seed
does not establish a general improvement across seeds.

If the candidate fails, retain v5 as the installed release and report the
failure. Further development must use development evidence and an evaluation
plan that does not select against exposed held-out outcomes. Do not relabel a
failed candidate as an achieved improvement.

## Compute and checkpoint preservation

The existing single-GPU job is the live training source. Preserve its dataset,
trainer/optimizer/RNG state, code hashes, and package versions before migration.
Use a single faster GPU if a resume can preserve the training recipe. A
multi-GPU rewrite is not assumed equivalent: device placement, loss reduction,
gradient synchronization, sample order, and checkpoint ownership need evidence.
Do not start another full run simply because a monitoring client disconnected.

Research checked before infrastructure changes:

- Existing `locallm/cloud_train.py`: detached Modal jobs, persistent volumes,
  subprocess logs, and periodic volume commits. It is read as prior art;
  changes for this run stay in dawnr's `t/` pipeline.
- [Modal's resumable training example](https://modal.com/docs/examples/long-training):
  checkpoints in volumes and detached execution survive client disconnection.
- [Modal GPU configuration](https://modal.com/docs/guide/gpu) and
  [volume documentation](https://modal.com/docs/guide/volumes): verify a real
  allocation and persist its result before relying on that compute path.
- [Transformers Trainer](https://huggingface.co/docs/transformers/v5.0.0/trainer):
  resume restores optimizer and RNG state, with limits on deterministic replay.

Working receipts and logs live under `t/out/v6-20261018/`. Publication requires
reproducible artifacts, checksums, a model card, passing release checks, and a
commit on main. Whole-system control remains outside this work.

## Matched route fixed before new model evaluation

The recovered notes distinguish two routes that both allowed 17 calls: prompted
baselines took one greedy and sixteen sampled answers, while the released
student used Python first. The new paired comparison uses the latter for both
v5 and v6, through the unchanged `spec_first.py` prompts and acceptance gates:
three Python attempts, five specification attempts, up to three kept
specifications with three proof attempts each. This is at most 17 calls per
problem, each capped at 1,024 new tokens. Greedy attempts come first; sampled
attempts use temperature 0.7 and top-p 0.95, without top-k, min-p, or repetition
penalties. Thinking is disabled.

Both models run at Q8_0 through llama.cpp commit
`f1cee9941b0e843ea260bf8dd9a090fbd9711b6a`, with the same server configuration.
`recipes/v6_server_route.py` adapts the decoder only. Its per-request seed is a
hash of the stage and exact prompt, independent of batch membership. This is a
new matched reading of the installed models, not a byte reproduction of v5's
historical full-precision HF sampling. Preserve and report both the historical
reference and this new paired baseline; the absolute 18/12/27 floors still apply.

The fixed 95-problem development panel is measured first. The 182-problem panel
and 33 supplied specifications are frozen separately. Cached requests bind the
model and server identity, and the run protocol binds code and input hashes.
A successful process exit alone cannot mark generation complete: every panel
id needs an outcome and every accepted answer needs a saved record.

## Continuation at step 400

All six historical judge-count discrepancies were replayed successfully on
every usable stored output. The slow case first timed out with a shorter
recheck budget and then passed under the original default budget, with a
55.948-second slowest case. No source program or expected output was changed.

A ten-update H100 throughput probe resumed a separate copy of checkpoint 300
and ended at 310. It took 124.2 seconds, or 12.42 seconds per update. The
12-second prediction was written after launch but before reading the result,
so this is exploratory; that prediction was missed. The observed update time
was still lower than the A100's roughly 16–18 seconds. Resource placement uses
that observed speedup, without treating it as evidence of better answers.

The actual training run saved and committed checkpoint 400 before its A100
container was stopped. All ten checkpoint files were hashed again. Its adapter
was also retained separately for development measurements. H100 resumed that
checkpoint and advanced beyond it; the benchmark's weights are not involved.

Google Cloud's L4 runs the v5 development route. A separate 16-vCPU, 128-GB CPU
worker builds the seven-prover environment from the engine's pinned Dockerfile
around the same dawnr source. The AWS two-prover control recorded some SPARK
twin timeouts; these are not passes and require replay on the full environment.
The larger worker has an eight-hour deletion deadline.

## Export and development checkpoint, before its evaluation

The retained step-400 adapter is exported and measured on the fixed 95-problem
development panel while training continues. This validates the export route
and provides an early development measurement. It is not a held-out run or a
release decision. The completed five-epoch run remains the primary candidate.

Export follows the existing `student_sft.merge` and October 11 export recipe:
load the pinned, unquantized base in bf16, attach the saved adapter with PEFT,
merge it, then use the pinned llama.cpp converter for Q8_0 without MTP. The base
is selected explicitly because the adapter's original absolute cache path is
not portable. Original adapter files remain unchanged. Input and output hashes,
the model revision, and converter revision accompany the export. PEFT's
[merge interface](https://huggingface.co/docs/peft/package_reference/lora#peft.LoraModel.merge_and_unload)
and the [pinned converter](https://github.com/ggml-org/llama.cpp/blob/f1cee9941b0e843ea260bf8dd9a090fbd9711b6a/convert_hf_to_gguf.py)
were read before implementation.
