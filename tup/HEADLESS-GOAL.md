# TUP native x86_64 installation and headless operation

## Goal prompt

Turn the TUP Linux From Scratch system in this repository's **tup/** directory into an installable, native x86_64 operating system for the desktop described below. Deliver a Ventoy-compatible live installer ISO, a working installation on the explicitly selected physical disk, protected remote access from the owner's MacBook, and separately tested compartments for workloads. Keep TUP's source-built base, named deviations, per-step receipts and measured resource use.

Treat this primarily as an LFS and BLFS integration project. Finish native boot, installation, drivers, networking and remote recovery before building the compartment system. The installed TUP base and installer must work independently of QEMU and Windows. An external x86_64 VM is an optional development test tool. ARM64 work is out of scope.

The owner's workload model is a continuously running TUP host with disposable TUP side instances. Each instance has a package manager for installing the tools its workload needs. An explicit finish action discards that instance's installed packages, writable operating-system state and temporary files while the host and other instances continue running. Remote disconnect does not finish a session. Persist only explicitly selected workspace data or exported results. The package manager belongs inside the instance; package installation must not grant control of the host or mutate a shared template.

Use **trestoncuzzort/dawnr**, not the standalone tup repository. The owner explicitly chose this source and authorized the native TUP work; that choice takes precedence over the older repository direction to work in the split-out repository. Keep the changes in TUP and its supporting documentation. This does not revive the retired general computer-control features in dawnr's assistant.

Read AGENTS.md, this entire document, and the relevant TUP build recipes before implementation. Preserve the generated book scripts: express changes through named overrides, profiles, layers and packaging scripts. Reuse maintained upstream components after checking primary documentation and the repository's existing work.

The hurdle register below is part of this goal. Every row must remain tracked with an owner, dependencies, implementation reference, test command, evidence path and current status. Add newly discovered hurdles immediately. Reproduce retained-path static defects with focused tests before fixing them. A retired VM-only path may instead be resolved by a tested replacement plus evidence that the old path is absent from the required build/install/release dependency graph; retain the finding without requiring repairs to unused QEMU scaffolding. Never turn an unrun test into a pass or erase a blocker from the record because another milestone succeeded.

Work autonomously on research, code, disposable builds and tests. Use separate branches or worktrees for parallel workers and one integration owner. Keep credentials, keys, disk serials, SSIDs, private addresses and machine-specific provisioning out of this public repository. Do not publish a public service or give other people access as a side effect of enabling the owner's remote access.

Before any physical disk or USB erase, finish the artifact and disposable installation tests, then present the exact target identity and partition plan for confirmation. The owner's backup confirmation is already recorded; do not repeatedly ask whether Windows is to be replaced. It does not identify which of the two same-sized internal disks or which USB is to be erased. Recheck target identity immediately before applying the plan.

Continue until the acceptance conditions below have measured evidence, or report a specific dependency that requires physical access, a user decision or a missing device. A research document, a login prompt, or a successful VM boot alone does not complete this goal.

## Deliverables

1. A native x86_64 TUP hardware profile and reproducible build instructions, with a maintained kernel baseline, sources, patches, firmware, configuration and toolchain identities recorded.
2. A versioned **tup-<version>-x86_64-install.iso** containing a TUP live installer/rescue environment, a verifiable installation payload, and no dependency on a running host OS or QEMU.
3. A plan/apply installer for GPT, EFI System Partition and selected root/data layout, with exact-target checks, a dry run, payload verification, interrupted-install handling and a recovery path.
4. A native boot chain, persistent root discovery, physical network configuration and a receipted headless-access layer with authenticated owner enrollment.
5. Private remote administration and durable workloads from the MacBook, including reconnect, reboot, update, rollback, backup and restore procedures.
6. A receipted native GPU-compute layer, followed by QEMU-free disposable TUP instances with a package manager, explicit finish/discard and persistent-data controls, and a documented, tested policy for CPU/GPU allocation and cross-compartment access.
7. Versioned test reports, artifact hashes, exact-image inventories, installation evidence and an up-to-date hurdle register. Do not call the system formally verified or byte-reproducible unless those specific claims have their own evidence.

Assign bounded work with explicit interfaces and give every worker a different worktree or non-overlapping file ownership. Each worker must return evidence and unresolved findings, not just a success message.

Useful parallel assignments are build/provenance, EFI/live-media/installer, remote operations, and compute/isolation. With three worker slots, combine the first two or run compute research after boot work frees a slot. An independent reviewer checks each integration before physical installation. No worker independently formats devices, reboots the desktop, publishes services or changes firmware.

Native installation is the critical path. Isolation research can proceed in parallel, but its implementation must not delay diagnosis of the LFS boot and installer defects.

## Acceptance matrix

Choose and record exact versions, budgets and timing thresholds before running these tests. Suggested initial qualification is **10 warm reboots, 3 cold boots and a 24-hour mixed-workload soak**; these are proposed test counts, not evidence already obtained. Record any change to that test plan and its reason.

| Test | Required result |
| --- | --- |
| Build and negative controls | Native base/layers build from pinned inputs; changed-input resume and all injected failure controls behave correctly; receipts refer to original bytes and the exact final artifact |
| ISO and Ventoy | ISO starts in x86_64 UEFI tests; the same digest boots through the tested Ventoy version on the actual hardware; live root discovery and installer payload verification succeed |
| Installer safety | Correct target succeeds; wrong, mounted, source, changed, ambiguous and declined targets get zero writes; corrupt payload and interrupted install have explicit recoverable outcomes |
| Independent boot | With installation USB removed, the physical desktop boots the selected disk's TUP, without QEMU or Windows, and reports the installed artifact/version |
| Network and enrollment | Physical networking, DNS and time start without a console login; unique host identity and the enrolled owner key work; default/root/password and unauthorized access fail |
| MacBook handoff | From a different internet access network, open a new authenticated connection after native reboot; transfer a file, launch a job, disconnect/reconnect and retrieve correct output |
| CPU and GPU | A representative build/verification job and RTX 4080 CUDA/inference/training job produce expected results; hardware use and resource measurements substantiate the claims |
| Compartments | Two independent TUP guests and test users pass cross-file, cross-network, management-API, privilege and resource-exhaustion negative tests; selected GPU allocation policy works; in-guest package install/run/finish/recreate passes while host and peer stay running |
| Update and recovery | Corrupt artifact is refused; bad candidate kernel/network configuration rolls back; Ventoy rescue and independent data/guest restore work |
| Reliability | Declared reboot/cold-boot/soak plan passes; failures, throttling, memory pressure, recovery times and management latency are retained in the report |

Completion means the declared operating envelope is demonstrated. It does not mean every possible failure is impossible. An unmet required security, boot, recovery or hardware gate keeps the relevant milestone incomplete. Optional public admission and optional advanced driver-domain/verified-boot features must have explicit scope decisions; deferral must name the lost capability and cannot silently weaken the required owner-access or workload-isolation outcomes.

## Decision queue

Ask only when the answer blocks the next concrete stage. Continue independent work while waiting.

- Exact internal installation/storage roles and USB erase target, identified privately by stable identity rather than disk number alone.
- Wired Ethernet availability versus supporting the active USB Wi-Fi path.
- Private remote-access control plane and endpoint/relay preference.
- Production Secure Boot and disk-encryption/unattended-unlock policy.
- Local versus independently remote recovery after the MacBook leaves the desktop's location.
- Later compartment design and GPU trust/allocation policy, based on measured native support.
- Invited-user versus public service admission, before enabling non-owner access.

## Evidence handling

Store public-safe recipes, manifests, test fixtures and redacted reports with the project. Keep machine enrollment, private keys, Wi-Fi credentials, disk identifiers and personal network details in a separate protected local configuration. Record source commit, architecture, profile, dependency hashes, test inputs, observed outputs, exit status, logs and artifact hashes for each result.

Statuses should progress through **open**, **reproduced or characterized**, **implemented**, and **verified**. A documented choice can resolve a design row; a code change cannot resolve a runtime row without its test. An explicitly accepted deferral records scope and consequences rather than reporting a pass.

At every handoff, state the last verified stage, newly found hurdles, current branch/worktree, artifact locations, pending decisions and the next runnable action. Preserve this register throughout the project.
